# Day 01: System Architecture and Environment Setup

## 1. Stage Objective
In this initial stage, we establish the foundational understanding of developing Windows desktop applications with Embedded Wizard 15, lay out the project directory structure, and understand the critical threading model required to keep a serial-communicating GUI completely responsive.

---

## 2. Why We Are Doing This Step
Embedded Wizard is primarily renowned for embedded GUIs on microcontrollers (STM32, NXP, etc.), but its Windows Platform Package translates Chora UI code into standard ANSI C and links with native Windows APIs (DirectX/OpenGL and Win32). 

Unlike frameworks like Qt or WPF where UI and background code often blur together:
- **Chora is single-threaded**: The entire Embedded Wizard runtime runs strictly within the main Windows GUI message loop.
- **Blocking I/O will freeze the GUI**: If serial port communication (RS485 polling, waiting for bytes, timeouts) or disk file I/O (writing CSV logs) is run directly in Chora, Windows will show "Application Not Responding" and the UI will lag or lock up.
- **Strict Decoupling is mandatory**: We must establish a clear boundary where C++ worker threads handle hardware communication, timeouts, and logging, while Embedded Wizard only handles presentation and user interaction.

## 5. Understanding the Embedded Wizard Windows Execution Loop

Inspect `WindowsSimulator/Application/Source/ewmain.c`. The core application loop runs as follows:

```c
int EwMain( int aArgc, char* aArgv[] )
{
  /* 1. Initialize Display, Keyboard, Cursor drivers */
  EwBspDisplayInit( ... );
  
  /* 2. Initialize our Native Device Engine */
  DeviceDriver_Initialize();

  /* 3. Initialize the Embedded Wizard Root Application */
  rootObject = EwInitRootObject( ApplicationApplication );

  /* 4. Windows Event Loop */
  while ( !EwWindowClosed )
  {
    /* Processes Chora timers, UI animations, redraws dirty regions */
    EwProcess();

    /* Process pending invocations scheduled from background threads via EwInvoke/EwInvokeCopy */
    EwProcessInvocations();

    /* Let Windows handle Win32 window messages */
    EwBspOsDelay( 5 ); 
  }

  /* 5. Cleanup */
  EwDoneRootObject( rootObject );
  DeviceDriver_Deinitialize();
  return 0;
}
```

### Why this is critical:
Notice `EwProcessInvocations()`. When our background C++ RS485 polling thread receives fresh sensor data from the chamber, it calls:
```cpp
EwInvokeCopy( UpdateGuiCallback, &snapshot, sizeof(snapshot) );
```
This safely enqueues a function pointer onto the Embedded Wizard invocation queue. During the next frame pass in `ewmain.c`, `EwProcessInvocations()` executes `UpdateGuiCallback` safely **inside the UI thread context**, avoiding race conditions, memory corruption, and GUI tearing.
